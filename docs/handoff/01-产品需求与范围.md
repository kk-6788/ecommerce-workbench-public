## B. 为可执行性作出的默认设计（DEFAULT，不伪装成用户原话）

1. 首版优先验证淘宝/抖店经营数据、1688供货、抖音短视频发布；依据现有业务材料，实际账号与字段在T03核验。
2. 本地FastAPI网页、Jinja2模板、原生JS/CSS、SQLite和单独任务worker；不用React/Node构建链、Redis、云数据库或多租户。
3. 首轮验收用一个证据充分的宠物商品，随后5商品档案批次。每个验收商品至少准备一套图和一条成片；这不是强制每周每款生成多条视频的业务配额。
4. 新品启动默认清单：链接/属性/规格/价格/库存/履约检查 → 素材审阅 → 确认上架 → 视频审阅及发布 → 回收数据 → 复盘。优惠活动只有在具体方案获准后执行。
5. 当前词池30词为导入与历史兼容基线，不代表已选出30个商品。没有证据，不批准进入实际执行层。
6. 本地服务默认127.0.0.1:8510；用户启用局域网模式后才能监听本机局域网地址。不得自动开公网隧道。
7. 不把“启动”解释为生成虚假订单、虚构评价或自动找人下单；既有创作者笔记是待评估输入。

## C. 首版明确不做

面向他人的SaaS、会员付费系统、多人权限矩阵、原生手机App、云端常在线服务、全品类专属策略、大规模并发抓取、自主花费、自主调权、仅凭模拟结果宣布真实连接器完成。

未来研发模式只保留strategy_mode和知识来源，不在首版建设打样/研发全流程；以后经用户要求再扩充。

## D. 每个商品的作业与产物

| 步骤 | 要留的产物 | 用户介入 |
|---|---|---|
| 机会发现 | 意图簇、关键词证据、来源时间与样本口径 | 查看或调整候选方向 |
| 货源核验 | 具体规格、报价、运费、供应商及证据缺口 | 页面无法确认时补证 |
| 选品 | 分层、硬约束结果、理由、预测快照 | 确认进入试验/执行的候选 |
| 图制作 | 主图/SKU图/详情图、事实核对、版本与费用 | 逐笔收费审批，审图 |
| 视频 | 选题、脚本、素材、成片、版本与费用 | 逐笔收费审批，审片 |
| 上架启动 | 平台字段、具体发布内容、动作预览与执行回执 | 确认具体外部动作 |
| 经营 | 同商品/店铺/日期/渠道的指标，缺失项明确 | 登录过期时处理登录 |
| 复盘 | 经营判断、可能因素、支持与反驳证据、验证卡 | 选择下一步动作 |
| 学习 | 历史预测与结果对照、校准提案 | 接受/拒绝新模型版本 |

## E. 页面与交互验收

主导航：今日工作、选品货源、商品档案、图与视频、上架启动、经营复盘。费用审批放在今日工作和相关商品页，不能藏在调试页。

今日工作要看见：每个商品当前阶段、阻塞原因、下一步、待审批金额、证据更新时间。不得把“当前系统时间”显示为数据更新时间。

商品档案包含来源证据、规格、货源、模型版本、图片和视频版本、平台链接、操作时间线。旧版本可查看，已发布素材不被后续生成覆盖。

审批页面展示内容差异、对应商品与账号、预计费用/上限、计费单位和失败收费说明。只有同意、拒绝和取消，没有默认勾选或倒计时自动批准。

桌面以表格和详情视图方便比较；手机次要路径只要求主要记录、素材预览及审批可用。界面中文字不能暴露数据库表名、provider异常栈或技术密钥。

## F. 仍然需要真实输入的事项及处理

| 条件 | 如何确定 | 缺失时状态 | 可以继续的工作 |
|---|---|---|---|
| 店铺/供货页已登录 | T03只读能力核验 | WAITING_INPUT / NEEDS_LOGIN | 核心模型、UI、模拟接口测试 |
| 图视频生成供应商、价格 | T03登记能力与报价，费用逐笔确认 | WAITING_APPROVAL或CAPABILITY_UNAVAILABLE | 素材整理、脚本、审核界面 |
| 具体SKU事实/授权素材 | 从真供货页与用户资料核对 | NEEDS_EVIDENCE | 其他商品与结构实现 |
| 原始经营报表 | 读取后台或用户提供导出，核对口径 | OBSERVING / INSUFFICIENT_DATA | 指标导入验证、复盘框架 |
| 明确的“扩大投入”阈值 | 用户在试验卡设置，留版本 | 暂不自动建议SCALE | 其他结果记录与定性分析 |

不要把这些条件设为整个项目无限等待的理由，也不要替用户伪造它们。
