# Problem Discovery

## Objective

Define the problem before evaluating the solution.

A product opportunity should not begin with:

> We should build X.

It should begin with:

> Who has what problem, under what conditions, and why does it matter?

---

## Core Questions

Ask:

- Who has the problem?
- In what situation does it occur?
- What triggers it?
- How often does it happen?
- How painful is it?
- What is the consequence of not solving it?
- What does the user currently do?
- Why is the current solution insufficient?
- What outcome does the user want?

---

## Problem Statement Template

> [User] experiences [problem] when [context], currently uses [alternative], but suffers from [limitations], creating an opportunity to [desired outcome].

---

## Weak vs Strong

Weak:

> Pet owners need a better water bottle.

Strong:

> Pet owners who spend long periods outdoors struggle to provide clean drinking water because current bottle-and-bowl setups are inconvenient, leak, or are difficult to clean.

---

## Problem Quality Test

A problem is stronger when:

- It is frequent
- It is painful
- It has meaningful consequences
- Users already spend time or money solving it
- Current alternatives have visible shortcomings
- The target user is identifiable
- The context is specific
- Evidence exists beyond opinion

---

## Anti-Patterns

Avoid:

- Turning a feature request into a problem statement
- Treating competitor behavior as proof of user need
- Using vague users like “everyone”
- Defining a problem so broadly that any solution fits
- Confusing business goals with user problems
- Assuming a problem is important because it exists

---

## Output

For a product opportunity, output:

1. Target User
2. Trigger / Context
3. Problem
4. Current Alternative
5. Pain / Consequence
6. Desired Outcome
7. Evidence
8. Open Questions
