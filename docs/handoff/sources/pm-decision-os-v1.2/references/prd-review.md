# PRD Review

## Objective

Ensure a PRD is a decision document, not just a feature specification.

A strong PRD connects:

Problem  
→ Evidence  
→ User  
→ Goal  
→ Solution  
→ Requirements  
→ Metrics  
→ Risks

---

# 1. Required Sections

## Background
Why now?

## Problem
What problem exists?

## User
Who has it?

## Evidence
What proves it?

## Goals
What outcome should change?

## Non-Goals
What is explicitly excluded?

## Solution
What is proposed?

## User Stories
How will users interact with it?

## Requirements
What must the product do?

## Acceptance Criteria
What counts as complete?

## Metrics
What proves success?

## Risks
What could fail?

## Dependencies
What must happen elsewhere?

## Open Questions
What remains unresolved?

---

# 2. Audit Questions

### Problem
Is the problem specific and user-centered?

### Evidence
Is there behavioral or transaction evidence?

### Solution
Does the proposed solution directly address the problem?

### Scope
Is MVP separated from future scope?

### Requirements
Are requirements testable?

### Metrics
Are success metrics defined before launch?

### Risks
Are failure modes acknowledged?

### Non-Goals
Is scope control explicit?

---

# 3. Severity

Use:

CRITICAL  
HIGH  
MEDIUM  
LOW

For each issue provide:

- Problem
- Why it matters
- Evidence
- Fix

---

# 4. Common PRD Failures

- Feature first, problem later
- No user evidence
- Goals are outputs instead of outcomes
- No Non-Goals
- Requirements too vague
- No acceptance criteria
- Metrics are vanity metrics
- No kill criteria
- Risks buried or ignored
- Roadmap presented as certainty
